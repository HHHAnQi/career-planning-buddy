# Rubric 锚点示例草案 v1（2026-08-25，待两位标注者仲裁）

> 目的：把人-人一致性（当前 kappa 0.03–0.12）拉到 0.7 以上。
> 用法：每个锚点 = 真实规划输出 + 建议共识分 + 该分所钉死的判读规则。
> 仲裁后锚点进入 rubric 文档与 judge prompt（同尺同例）。
> 三列分数：huanqi / ly / judge(DeepSeek v4-pro)。

## 分歧的三个病根（从数据归纳）

**病根 A：方向假设该不该罚（D1）**——画像未指明具体技术方向时，规划自选
Java/React/Spring 是否算“强加用户没提的目标”？ly 严格按 rubric 原文罚
（1-2 分），huanqi 接受合理推断（4-5 分）。**注意：rubric 原文站在 ly 一边。**

**病根 B：流程完整性该不该罚（D3/D4）**——环境搭建直接跳到前后端联调、
缺开发环节。huanqi 罚到 1 分，ly/judge 完全不考虑（5 分）。**rubric 补充
判据（流程完整性条款）站在 huanqi 一边**（该条款已入 rubric 文档但 judge
prompt 在回滚时未带——锚点就位后一并同步）。

**病根 C：预算用不满该不该罚（D3）**——用户声明 480 分钟/天而任务只排
了零头。huanqi 罚，ly 不罚。**预算利用率条款站在 huanqi 一边。**

## 锚点 1（D1·方向假设-罚）case: repair-03 —— 建议共识分：**2**

规划：中级职业转换用户，规划直接进入 Java 集合源码/并发/线程池。
分数：4 / 2 / 5。
**钉死规则**：画像只说“职业转换准备 + 中级”，未指明 Java 方向。规划选择
一个具体技术栈方向且未在 assumptions 中声明 = 目标假设，D1 ≤2。
方向与 goal_type 一致的**泛化**准备（如“后端基础”）可接受，**具体技术栈
选型**不可，除非请求或画像提及。

## 锚点 2（D1·方向明确-不罚）case: create-01 —— 建议共识分：**4**

规划：job_search/applying 用户，任务围绕简历梳理与首批投递。
分数：3 / — / 3-5（huanqi 罚的是“四周只给一周”，非方向问题）。
**钉死规则**：方向来自画像 goal_type 本身（求职准备→简历+投递）不算假设。
“请求要四周只给一周”属于范围偏离，在 D1 扣 1 档（5→4），不与方向假设叠加。

## 锚点 3（D3·流程完整性-重罚）case: repair-04 —— 建议共识分：**1**

规划：全栈项目从 Node.js/VS Code 安装直接跳到前后端联调，无任何开发环节。
分数：1 / 5 / 4。
**钉死规则**：目标为“完成一个项目”的规划，任务序列必须覆盖该目标的必要
环节（搭建→开发→联调→部署）。缺失核心环节（无开发直接联调）D3 = 1，
无论每步写得多具体。**具体性不能弥补结构性缺失。**

## 锚点 4（D3·预算利用率-中罚）case: create-12 —— 建议共识分：**3**

规划：用户声明 480 分钟/天，任务安排明显用不满（大量空转空间）。
分数：2 / 5 / 5。
**钉死规则**：单日任务合计 < 声明预算的 60% 且未说明原因（如刻意减量）
→ D3 ≤3。用满是默认预期；规划若判断用户该少排，须在 assumptions 中声明。

## 锚点 5（D4·泛化推进-中罚）case: replan-04 —— 建议共识分：**3**

规划：一周全是“打开复习笔记、阅读标记重点、完成习题 A”类泛化复习，
与 weekly_focus 无具体对应（“完成习题A”的 A 是什么无从知晓）。
分数：3 / — / 5。
**钉死规则**：日期连续只是不扣分底线；每个任务须可对应到当周 focus 的
**具体** success_signal。“复习/练习/学习”类无具体对象的任务 ≥3 个 → D4 ≤3。

## 锚点 6（D2·空证据=3，防 1 分误读）case: 任意 —— 建议共识分：**3**

证据目录为空、规划无引用（当前工作表全部 case）。
分数：3 / 3 / 3（校准后已一致）。
**钉死规则**（防回退）：空目录 + 零引用 = 3（不可验证，无造假）；
仅当引用目录中不存在的 id 才 = 1。此锚点已验证有效，保留为防退化桩。

## 仲裁流程建议

1. 两位标注者各自独立看 6 个锚点的建议共识分，标同意/不同意+理由；
2. 分歧的锚点讨论定稿——**分歧本身就是要钉死的规则**；
3. 定稿后：锚点写入 `docs/standards/plan-quality-rubric.md`；同步进 judge
   prompt（恢复流程完整性/预算利用率措辞，v9）；两位标注者对锚点外的
   3-5 个 case 重标一次，验证人-人 kappa ≥0.7；
4. 达标后 judge 以同一锚点集重新校准。

## 预期

锚点 1/3/4 各自把一个病根钉死；若仲裁采纳，huanqi 与 ly 的评分函数将
共享同三个规则，D1/D3 的人-人 kappa 预计从 ~0.1 升至 0.6+。
