## 流程全景图

```
阶段 0  工程基线        ← 你现在在这里（PRD 已定稿，下一步立刻开始）
  │
阶段 1  架构设计 HLD     ← 与原型图并行
  │
阶段 2  详细设计 LLD     ← 首版每模块 5 篇核心分册
  │
阶段 3  纵切样例         ← 1 条端到端链路跑通
  │
阶段 4  批量开发         ← 照纵切样例扩散
  │
阶段 5  测试与验证
  │
阶段 6  部署与上线       ← 远期，本地开发完成后启动
```

**核心原则**（来自 AIGOV 迁移）：
1. 工程基线先于业务代码一天到位
2. 纵切先行，不要平行铺开所有模块
3. 每模块设设计冻结点——5 篇核心分册写完就开始编码
4. 接口契约先行——双服务面向同一 schema 开发

## 阶段 2：详细设计（LLD）——首版每模块 5 篇核心分册

### 目的

为每个模块定义可落地的详细设计——API 接口、状态机、数据库表、实施计划。首版只做 5 篇核心分册，其余按迭代补。

> AIGOV 教训 P-01：设计覆盖率远超代码覆盖率是反模式。dazi 设设计冻结点——5 篇写完就开始编码。

### 前置条件

- 阶段 1 完成（HLD + 原型图就位）

|---|---|---|---|---|---|---|
| 建档 | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| 生成规划 | ✅ | ✅（双 API） | ✅ | ✅ | ✅ | ✅（核心） |
| 今日任务 | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| 复盘 | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| 记忆管理 | ✅ | ✅ | ✅ | ✅ | ✅ | — |
| 安全分流 | ✅ | ✅ | ✅ | —（无独立表） | ✅ | — |

每篇分册的内容要求：

| 分册 | 内容 |
|---|---|
| 00 业务流程交互图 | mermaid 序列图（含 Java↔Python 跨进程交互） |

## Spec-Driven 工作流（贯穿阶段 2-5）

每个具体功能开发时，走五段式：

```
改动到来
  │
  ├─ ① Clarify 澄清（达阈值才持久化）
  │     └─ 边界/假设不明确 → 登记到 clarify.md
  │
  ├─ ② Plan 持久化（plan.md 含 mermaid 时序图）
  │     └─ 跨模块 / 跨服务 / 触状态机 / 新增 API / 新增表 → 必须持久化
  │
  ├─ ③ Tasks 持久化（tasks.md 带 [P] 并行标记）
  │     └─ 跨上下文 / 新增 API / 新增表 → 必须持久化
  │
  ├─ ④ Implement 实现
  │     └─ 按 api → domain → application → infrastructure → interfaces 顺序
  │
  └─ ⑤ Verify 验证
        └─ mvn verify + pytest + ruff + import-linter + ArchUnit + 自愈回灌
```

持久化判定矩阵：

| 改动类型 | Clarify | Plan 文件 | Tasks 文件 |
|---|---|---|---|
| Bug fix < 30 行 + 单模块 | 必做（口头确认） | 否 | 否 |
| 单特性 / 跨模块 / 触状态机 | 必做 | 是 | 可选 |
| 跨服务（Java↔Python）/ 新增 API / 新增表 | 必做 | 是 | 是 |
| 架构级（新增上下文 / 中间件） | 必做（需评审） | 是 | 是 |
| 实验 / 探索 | 可省 | 否 | 否 |
