# AI 虚拟规划搭子 — 可行性分析报告

> 版本：v1.0 / 2026-07-10
> 性质：进入 PRD 正式重写前的可行性验证报告
> 适用：2 人团队 + AI 编程工具 / 个人项目 / 面向大厂面试 / 未来上线小程序商城

---

## 0. 一句话结论

**项目可行，但需要在三处做关键调整：**

1. **技术方案整体可行**——LangGraph 4 节点工作流是标准用例，2 人 + AI 工具 4 周可跑通 MVP。但要锁定技术栈、控制模型成本。
2. **市场需求真实存在**——竞品调研确认"诊断→规划→今日低压力任务"的链路是市场空白，有机会卡位。
3. **合规是最大风险**——个人主体无法上线，必须注册企业主体 + 完成算法备案（周期 2–6 个月），这段时间先做技术 PoC 和面试 demo。

**建议路径**：先做 4 周 MVP 用于面试与技术验证（本地服务器跑通），同步启动企业注册与算法备案，备案下来后再正式上线小程序。

## 一、市场可行性

### 1.1 竞品格局

| 赛道 | 头部产品 | 共性缺口 |
|---|---|---|
| AI 求职辅导 | 超级简历、BOSS 直聘、牛客网 | 普遍集中在"简历/刷题/招聘匹配"等执行末端，无人做"先做什么"的前置规划 |
| AI 考公备考 | 粉笔、华图、中公 | 重内容/课程/题库，AI 只用于批改；零基础用户"怎么开始"是空白；1V1 规划是人工高客单、不可规模化 |
| AI 任务管理 | 番茄 TODO、滴答清单 | 只管"强制你做"，不管"该做什么"；放大而非缓解启动焦虑 |
| 通用大模型 | 豆包、Kimi、通义、智谱、DeepSeek | 能力够但都是被动问答；无结构化"整体方向+本周+今日任务"输出、无任务状态闭环、无统一记忆管理 |

### 1.2 三大空白点

- **空白 1**：无人做"诊断→规划→今日小步"的前置链路
- **空白 2**：无人做"低压力启动"定位（市场全是高压备考/强制自律）
- **空白 3**：无人做"受控多 Agent + 统一记忆 + 来源核查"的工程化产品化封装

### 1.3 差异化机会与威胁

**机会**：
1. 抢占"AI 规划搭子 = 整体方向 + 本周重点 + 今日 1-3 个低压力任务"的输出形态心智
2. 以"1-3 个低压力任务 + 最小启动动作 + 完成标准"对冲高压产品
3. 三场景横切（求职/考公/实习），避开与粉笔/牛客纵深竞争
4. Controlled Agentic Workflow + Memory Service + 来源核查是工程化护城河，可作为面试技术亮点

**威胁**：
- 通用大模型（尤其豆包、Kimi）随时可向下覆盖，速度是防御关键
- 微信小程序生态内可能有同类长尾产品无法被搜索索引，需人工踩点

### 1.4 对面试场景的加分

面试官对项目的评估维度：业务理解 + 技术深度 + 工程化 + 能讲清楚。这个项目恰好命中：
- 业务：真实痛点、有用户分层、有验证指标
- 技术：多 Agent 编排、RAG、状态机、双服务架构、可观测性
- 工程：受控降级、来源审计、敏感记忆、合规设计
- 讲故事：从模糊想法到可控 Agent 工作流的完整决策链

**结论：市场需求真实，作为面试项目具备完整的"故事性 + 技术深度"。**

## 二、技术可行性

### 2.1 LangGraph 4 节点工作流（✅ 可行）

| 维度 | 结论 |
|---|---|
| 当前版本 | LangGraph v1.2.x（1.x 主版本，生产就绪，Klarna/Replit/Elastic 等在用） |
| 状态图 | ✅ StateGraph，支持条件分支、并行节点 |
| 持久化 | ✅ Durable execution + Checkpoint，失败可从断点恢复 |
| Human-in-the-loop | ✅ interrupts 机制（可用但本项目不需要） |
| 结构化输出 | ✅ 配合节点 schema |
| 有限 Loop | ✅ 条件边 + recursion_limit，重写 ≤2 次属标准 pattern |
| 4 Agent 难度 | 中低，2 人约 3-5 天跑通 MVP |
| 已知坑 | 合并 reducer 易覆盖 state；调试强依赖 LangSmith；recursion_limit 默认偏低；与 langchain-core 版本强耦合 |

**建议**：
- pin 版本 `langgraph==1.2.x` + 配套 `langchain-core`
- 必须接入 LangSmith 做可观测性（调试主要风险）
- 重写循环用 state 计数器字段显式控制，不要只靠 recursion_limit

### 2.2 LLM 成本与延迟（✅ 可控）

**主流国产模型价格参考（2026，API 输入价格量级）**：

| 模型 | 定位 | 价格量级（输入/百万 token）| 适用节点 |
|---|---|---|---|
| DeepSeek V4 | 强推理 + 便宜 | 低（¥1-4 级别） | 计划生成、搜索蒸馏 |
| 智谱 GLM-4.5/4.6 | 通用强模型 | 中低 | 计划生成 |
| 通义 Qwen3-Max/Plus | 通用强模型 | 中低 | 备选 |
| DeepSeek/GLM 小模型 | 轻量 | 极低 | 诊断、校验、分类 |
| 豆包 lite | 轻量 | 极低 | 诊断、校验 |

**单次 plan_run 成本估算**：
- 诊断节点（小模型，~1K 输入 + 200 输出）：≈¥0.001-0.005
- 搜索蒸馏（强模型，~5K 输入 + 1K 输出）：≈¥0.02-0.05
- 计划生成（强模型，~4K 输入 + 1.5K 输出）：≈¥0.02-0.05
- 校验陪伴（小模型，~3K 输入 + 500 输出）：≈¥0.003-0.01
- 合计单次 ≈ **¥0.05-0.12**（不含联网搜索）
- 含联网搜索（第三方 API）：+ ¥0.03-0.1
- **端到端单用户单次 ≈ ¥0.08-0.2**

**延迟估算**：
- 4 节点串行：约 8-20 秒（含联网）
- 用户可接受范围：规划类任务 ≤15-20 秒可接受（非实时聊天）
- 建议：先返回"正在为你生成规划..."的过渡态，必要时做计划生成的流式输出

**建议**：
- 模型分层：诊断 + 校验用小模型；搜索蒸馏 + 计划生成用强模型（DeepSeek V4 主选、GLM 备选）
- 全部用国产模型，避免数据出境合规问题
- 面试阶段日活低，成本可忽略；上线后按 ¥0.15/次 预估，日活 1000 则约 ¥150/天

### 2.3 架构与部署（✅ 可行）

**双服务架构**：

```
微信小程序 → Nginx(443) → Java(Spring Boot, 8080)
                          → Python(FastAPI+LangGraph, 8000)
                          → PostgreSQL(5432, 含 pgvector)
                          → Redis(6379, 缓存/会话)
```

| 组件 | 选型 | 理由 |
|---|---|---|
| Java 后端 | Spring Boot 3.x | 业务事务、用户/计划/任务 CRUD、小程序 API、后台管理 |
| Python Agent | FastAPI + LangGraph 1.2.x | Agent 编排、LLM 调用、搜索蒸馏 |
| 数据库 | PostgreSQL + pgvector | 一套库搞定关系型数据 + 向量检索，2 人团队少维护一个组件 |
| 缓存 | Redis | 会话、短期上下文、限流 |
| 反代 | Nginx | 统一入口、HTTPS、小程序合法域名 |
| 部署 | Docker Compose | 单机一键起所有服务 |

**Java 调用 Python**：HTTP REST（POST /agent/plan/run），同步等待。Trace 用 run_id 串联——Java 生成 run_id 传给 Python，Python 落 agent_steps 记录后由 Java 统一存库。

**部署方案**：
- 面试阶段：1 台 4C8G 云服务器（阿里云/腾讯云学生机或轻量，约 ¥100-200/月），Docker Compose 跑全部服务
- 上线后可升级到 8C16G + 独立 PostgreSQL

**ICP 备案**：服务器域名必须 ICP 备案（小程序合法域名要求），备案主体用企业。

### 2.4 RAG + 联网搜索（✅ 可行）

| 维度 | 推荐 | 理由 |
|---|---|---|
| 向量库 | **pgvector** | 已用 PostgreSQL，不需要额外维护 Qdrant/Milvus；个人项目数据量冗余足够 |
| Web Search | **第三方 API（Tavily 或 Serper）** | 比"模型原生联网"更可控、可拿到结构化来源；Tavily 有免费额度 |
| 经验原子抽取 | 半自动：强模型从经验帖抽取 → 人工审核入库 | 冷启动可人工整理 30-50 条高质量经验原子覆盖三个场景 |

**经验原子工程难点**：来源可追溯（source_ids）、适用人群标注（applicable_user）、风险提示（risk_note）需要人工标注质量。建议 MVP 阶段只做 30-50 条，面试 demo 够用。

### 2.5 小程序接入 LLM 内容安全（✅ 必须，见合规章节）

- LLM 输出必须先审后发：接入微信 `security.msgSecCheck` 或腾讯云天御
- 延迟增加约 100-500ms，规划类场景可接受

### 2.6 2 人团队 + AI 工具的开发可行性（✅ 可行但需精简）

**心智负担评估**：

| 模块 | 工作量 | 风险 |
|---|---|---|
| Java 后端（CRUD + 事务 + 后台） | 中 | 低，CRUD 成熟 |
| Python Agent（LangGraph + LLM + 搜索） | 中高 | 中，调试成本 |
| 微信小程序前端 | 中 | 低，页面不复杂 |
| 部署运维 | 低 | 低，Docker Compose |
| 合规/备案 | 低（但不做不行） | 高，周期长 |

**AI 编程工具加成**：Cursor / Claude Code 可将 CRUD、前端、脚本类工作提效 50-70%；Agent 编排逻辑需要人工设计但代码生成有辅助。

**降风险建议**：
1. **不要同时做 Java + Python + 小程序 + 后台四条线**——MVP 阶段后台极简（甚至先用 SQL 直接看数据），小程序只做核心 5 个页面
2. **技术栈不要追求最新/最炫**——Spring Boot 3 + FastAPI + PostgreSQL + Redis + Docker，全部是主流稳定栈
3. **不要过早优化**——先跑通端到端 1 次 plan_run，再谈性能、缓存、分层
4. **第一周必须出端到端 demo**——哪怕质量差，跑通"小程序发消息→Java→Python 4 节点→落库→小程序展示"这条链路是第一里程碑

**结论：2 人 + AI 工具 4 周可跑通 MVP；技术栈已收敛，风险可控。**

## 三、合规可行性（最大风险项）

### 3.1 核心结论

**个人主体几乎无法合规上线。** 三道硬门槛：

1. 微信"生成内容服务"类目**仅对企业/个体工商户主体开放**，且要求算法备案号
2. 《生成式人工智能服务管理暂行办法》要求上线前完成**算法备案 + 安全评估**，个人主体实操极难通过
3. 收集情绪/健康/家庭/财务等**敏感个人信息**，需单独同意 + 必要性论证，个人主体难以承担

**唯一路径**：注册企业主体（有限责任公司，注册资本认缴制）→ 企业认证小程序 → 算法备案 → 上线。

### 3.2 时间线

| 阶段 | 周期 | 可并行 |
|---|---|---|
| 企业注册 | 1-2 周 | — |
| 小程序企业认证 | 1-3 天 | 与企业注册并行后期 |
| 算法备案 + 安全评估 | 2-6 个月（首次驳回率高） | **与 MVP 开发并行** |
| ICP 备案 | 2-4 周 | 与上者并行 |
| 小程序类目审核 | 1-2 周 | 备案号下来后 |

**关键洞察**：算法备案周期 2-6 个月，正好与 MVP 开发 + 面试求职周期重叠。建议立即启动企业注册，并行做 MVP 技术开发。

### 3.3 合规 Checklist（红线项）

**🔴 阻塞上线的硬门槛**：

- [ ] 注册企业主体（有限责任公司）
- [ ] 小程序企业认证（¥300/年）
- [ ] 提交算法备案（深度合成 + 生成式 AI 类型）
- [ ] 备案号下发后申请"生成内容服务"类目
- [ ] 服务器域名 ICP 备案到企业名下
- [ ] 撰写隐私政策（敏感信息单独列）+ 用户协议（AI 生成内容免责）
- [ ] 实现敏感信息**单独同意**机制
- [ ] 实现删除权（15 个工作日内，含日志/备份）
- [ ] 使用**国内大模型 API**（避免数据出境）
- [ ] 接入微信 `security.msgSecCheck` 或腾讯云天御
- [ ] LLM 输出**先审后发**
- [ ] 高风险关键词词表 + LLM 分类器双重识别
- [ ] 心理危机固定话术 + 显示心理援助热线 **12356**
- [ ] 高风险触发后停止普通规划、不进入记忆候选
- [ ] 后台敏感文本脱敏展示
- [ ] AI 生成内容显著标识（"AI 生成"）
- [ ] 动态事实展示来源链接 + "以官方公告为准"
- [ ] **不做**医疗诊断/法律意见/金融建议/"保 offer"承诺

**🟡 MVP 后补**：
- [ ] 个人信息保护影响评估（PIA）书面文档
- [ ] 敏感字段数据库加密
- [ ] 违规内容人工复核流程
- [ ] 模型变更时重做安全评估

### 3.4 对面试 demo 阶段的影响

- 面试 demo 阶段**不需要上线**，本地服务器跑通即可，不存在合规问题
- 合规设计本身是项目亮点，可在面试中讲"我做了哪些合规前置设计"
- 真正上线小程序商城才需要走完上述 checklist

## 五、待决策问题（需用户确认）

### 5.1 产品边界
1. **三个场景在 MVP 是否都要做**？还是先聚焦 1 个场景（如"计算机求职"）做透，作为面试 demo 更聚焦？

3. **是否主动推送/提醒**？PRD 现在写"不做主动推送"，但"7 日回访率"指标似乎需要某种召回机制——是否保留微信模板消息提醒（每日 1 条"今天的任务准备好了"）？

### 5.2 技术决策
4. **Java 是否真的必要**？面试项目用 Java + Python 双语言会增加心智负担，是否考虑纯 Python（FastAPI 一套搞定业务 + Agent）？还是 Java 是技能展示需要？
5. **是否需要后台管理界面**？MVP 阶段是否直接用 SQL/命令行看数据，不做后台页面？
6. **经验原子库冷启动**：MVP 阶段人工整理 30-50 条，你能否提供初始的经验帖素材，或需要我设计采集流程？

### 5.3 合规与上线
7. **企业注册**：你是否已有公司主体？是否愿意为这个项目注册一家？
8. **算法备案**：是否愿意走 2-6 个月的备案流程？还是面试阶段本地 demo 即可，上线以后再说？
9. **模型选型偏好**：DeepSeek / 智谱 GLM / 通义千问，你有偏好吗？（影响成本与效果）

### 5.4 PRD 写法
10. **PRD 目标读者**：这份 PRD 是给你自己 + 1 位搭档看的，还是要能放在面试作品集里给面试官看？这影响技术细节的保留程度。
