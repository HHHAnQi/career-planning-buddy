# 检索规模实验结果（2026-08-26）

> 语料生成器（种子化、金标组合唯一性、断路器防死锁）+ GLM embedding-3 API + GPU bge-reranker。
> 完整矩阵：`python -m scripts.retrieval_scale_eval --sizes 100 500 2000`

| 语料规模 | 纯向量 | 词法 | Hybrid20 | Hybrid+Rerank20 | Hybrid+Rerank50 |
|---|---|---|---|---|---|
| ~26 chunk | 1.000 | 0.875 | 1.000 | 1.000 | 1.000 |
| ~127 chunk | 0.238 | 0.119 | 0.214 | **0.452** | 0.452 |
| ~504 chunk | 0.054 | 0.036 | 0.036 | **0.161** | **0.196** |

## 三个结论

1. **向量检索在规模下崩溃**：语料从 26 → 504 chunk（19 倍），纯向量 Recall 从 100% 崩至 5.4%——同域合成文本的 embedding 相似度无法在规模下区分目标与干扰。
2. **RRF 融合不救场**：hybrid 跟随较差通道的性能（504 chunk 时 3.6%≈词法的 3.6%）。
3. **神经重排是唯一幸存者**：500 chunk 时重排把 5.4% 拉到 19.6%（**3.6 倍提升**），且 rerank50 > rerank20（更多候选可挽救）。生产含义：当前单阶段向量检索在 10³+ chunk 规模不可行，必须用"粗召回→精重排"多级架构——这与业界 retrieve-then-rerank 标准模式一致。

## 死锁修复记录

语料生成器在 seed=2042（2000 chunk）下死锁：`marker_counter` 冻结导致 `(mc+1)%3==0` 恒真 → 每次进 golden 分支 → combo 已用 → continue（mc 不增）→ 无限循环。修复：连续 20 次 golden combo miss 后跳过 golden 身份直接生成干扰文档（断路器）。


## ⚠️ 方法论修正（2026-08-26 追加）

上述结论**存在严重的评测设计缺陷**：合成语料的 8 个 domain 在 127 篇文档中
平均每 domain 16-22 篇，同一 domain 的文档除公司名和随机数字外**内容几乎
完全相同**。查询语义上无法区分金标与近克隆干扰——任何检索系统都不可能在
"N 个近克隆中找唯一标记的那篇"的任务上表现好。

**诚实的修正**：
- 规模退化曲线的主要驱动因素是同质化程度上升（语料越大同 domain 文档越多）
  而非真实的检索规模效应
- 重排的 3.6 倍提升在同质语料上被夸大（它捕捉的是公司名/数字差异而非语义差异）
- "单阶段检索不可行"的结论**不能**基于此数据下达

**可信的结论**（来自 v2 硬化集的手写有区分度文档）：hybrid 融合在小语料
（12 chunk/case）上是最优模式（Recall 1.0/MRR 0.95）。规模效应的正确测试
需要扩展 v2 硬化集（30-50 case × 6-10 篇有真实区分度的文档）而非程序化
近克隆语料。
