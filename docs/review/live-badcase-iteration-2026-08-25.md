# Live 评测 Bad Case 归因与 Prompt 迭代实验记录（2026-08-25）

> 一次完整的"bad case 归因 → 假设 → 实验 → 测量 → 回滚"闭环。结论是**负结果**：
> prompt 规则增强对真实 GLM-4.7 的通过率无净收益，基线 prompt 被保留。
> 负结果本身是评测驱动开发的核心证据。

## 基线

真实 GLM-4.7 × stage5 × k=3（90 次）：硬门禁 **72.2%**。同口径剔除 3 个
mock-scripted case 后（27 case × 3 = 81 次）：**80.2%**。

## Bad case 归因（两类根因 + 一个数据集发现）

| 根因 | 证据 | 影响范围 |
|---|---|---|
| **REPLAN_CONTINUITY 违规** | 18 次校验失败；continue 模式要求 overall_direction 与源计划逐字一致（模型改写）或 adjust 模式缺 adjustment_reason | replan-01/02/05 全败、repair 类部分 |
| **TASK_UNIQUENESS 违规** | 4 次校验失败；任务标题/交付物跨天重复 | repair-02/04 |
| **create-07/08/09 是 mock 专属脚本** | 消息内嵌 `[mock:tool-memory]` 等标记——是 Mock Provider 的执行指令，不是真实信息需求信号；真实模型零工具调用且无法从上下文推断需要调用 | 3 个 case 在 live 模式**无效**（已从 live 统计剔除） |

## 实验矩阵（同一 27-case 口径，每版 81 次真实运行）

| 版本 | 变更 | 硬门禁 | 结论 |
|---|---|---|---|
| v5（基线） | — | **80.2%** | 保留 |
| v6 | 重规划逐字规则 + 任务唯一性强化 + 工具优先指令 | —（抽样即大幅回归） | 工具指令让"不该调工具的 case"调了工具（expected_match 精确匹配失败） |
| v7 | v6 但工具指令软化为"信息需求驱动" | 63.0% | replan 部分改善（0/3→1~2/3）但 create 类大面积回归 |
| v8 | 消融：仅保留重规划逐字规则 | 75.3% | replan-01 微升（0→1）但 replan-04 反降（3→1）、repair-03 降（3→2） |

## 结论与决策

1. **回滚到 v5**：所有增强版本均低于基线。数字说话，自我否决。
2. **失败主因不是 prompt 清晰度**：v8 的单变量消融证明即使精确陈述校验规则，
   GLM-4.7 的遵循仍不稳定——推理方差主导（大量 1/3、2/3 的部分通过），
   属于模型能力边界，不是指令问题。
3. **数据集发现**：create-07/08/09 的 `[mock:tool-*]` 内嵌指令使它们对 live
   无效。live 有效的工具 case 需要：真实种子的用户记忆 + 消息中包含引用该
   记忆的自然语言信号。这是扩量时的明确设计要求。
4. **下一步方向**（按预期收益）：换更强/更遵循指令的模型对比（变量是模型
   而非 prompt）；为 live 构造带真实信号的工具 case；repair/replan 的失败
   接受为当前模型能力基线，作为模型选型的决策输入。
