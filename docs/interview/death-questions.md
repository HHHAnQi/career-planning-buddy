# 10 道死亡问题满分应答话术（可背诵版）

> 用法：每题按「结论先行 → 结构展开 → 数据背书 → 边界承认」四段作答。
> 【】内是临场提示，不用背。总计约每题 60–90 秒口述量。

---

## Q1：「你这个项目不就是后端套了个 LLM 吗？哪有 Agent？」

**结论**：判断是不是 Agent 不看"有没有调 LLM"，看有没有"规划-行动-校验-修复"闭环——我的系统有五环闭环，且有量化数据证明每一环在工作。

**展开**：普通后端+LLM 是"请求进、文本出"，错了就错了。我的系统里模型承担 Agent 职责：意图理解（三分支路由）、任务规划（7 天计划拆解）、工具决策（memory/RAG/web 三工具自主调用）、自我修复（业务规则违规后的 LLM 修复）；代码承担生产职责：21 项确定性校验闸、预算硬限、断点恢复、降级模板。这两层是互补的——模型保证能力和泛化，代码保证上线不炸。

**数据**：模型一次通过率、工程修复占比、降级率我是分开度量的（plan_provenance 五标签），任何一环的贡献都可以单独拿出来看，这不是黑盒套壳。

**边界**：如果面试官认为"必须有自主多步循环才叫 Agent"——我的工具循环是有的（最多 2 轮、BudgetGuard 有界），我刻意不让它无限循环，因为生产 Agent 的循环必须有预算边界，否则就是烧钱死循环。补充：我第一轮基线对照曾把"享图骨架的 direct 臂"误当裸模型（它还有预执行记忆），配错能活到复核对账说明评测流程缺臂配置断言——现在 evals/v2/arm_invariants.py 在试跑前和评分时双点断言臂不变量，配错臂直接判无效，这类错误在机器层面无法存活。

## Q2：「为什么用 LangGraph？我看你这就是个固定流程，裸写函数链不行吗？」

**结论**：固定流程是业务决定的安全边界，不是图的全部——我的图有 3 处条件边、1 条修复回边、节点级 checkpoint 和图内并行，这四件事裸写函数链要么做不到、要么要自研 1000 行以上。

**展开**：第一，动态分支：风险闸二分支、意图三分支、校验二分支，声明式条件边让拓扑即文档，导出来就是流程图；第二，**原生并行**：意图路由后 fan-out 出 memory_loader ∥ evidence_loader 双节点同超步并发、context_builder 做 join——有专门的测试断言两个节点的执行区间真实重叠（tests/test_parallel_context_fanout.py），不是节点内 asyncio 的伪并行；第三，有界循环：校验失败走修复回边再回校验，循环次数由条件边加预算双重控制；第四，可恢复：每个节点 checkpoint 落 Postgres，带输入指纹校验，进程崩了从断点恢复不重复烧 LLM 调用；第五，状态管理：TypedDict 强类型 State，节点只返回增量，加新节点不改老节点签名。

**数据**：自研等价物（状态通道+条件路由+checkpoint）估算 800–1200 行且无社区验证；LangGraph 只用它的图语义，持久化我换成自研 Postgres 实现，因为恢复要和业务表的 lease/attempt 联动。

**边界**：如果项目是单次 LLM 调用的线性封装，我不会用 LangGraph——图运行时就是多余依赖。选型是"这个项目有分支、有环、有恢复需求，三条全占"。深挖 runtime 我也能接：超步并发写同 key 抛 InvalidUpdateError、path_map 不接受列表而路由函数可以返回列表、schema 外 key 静默丢弃、兄弟任务异常传导取消——五个机制全部踩过坑并做了最小复现（docs/architecture/langgraph-runtime-notes.md）。

## Q3：「模型工具调用触发率才 11%，你都预执行了，那模型不是被架空了吗？为什么还留工具列表？」

**结论**：预执行只接管"高频、固定、漏调代价高"的一条路径（引用历史的规划请求），其余所有场景模型保留完整的工具选择权——地板保下限，模型保上限。

**展开**：分层设计：L1，意图路由器检测到用户引用过去上下文（"之前/复盘/经验"这类标记）时，代码直接执行 memory_lookup，因为 live 数据证明模型在这条路径上不可靠（11% 触发）而业务上 78% 的规划请求引用历史；L2，其余场景模型自主决定调不调、调哪个、传什么参数、组合几次——比如"结合行业报告和我上次的复盘做新计划"这种组合任务，预执行根本枚举不完；L3，BudgetGuard 限 2 轮 4 次，防工具循环。注意 L2 的自主性有实测代价：终版 k=3 里 live-mem-01 有 2/3 trial 因模型附加了预期外工具调用导致精确匹配失败——自主性与确定性各有账，我都摆在台面上。

**数据**：预执行把这条路径的通过率从接近全败拉到大部分通过；消融实验（同代码切换 MEMORY_DISABLED）给出记忆层总贡献 +13.3pp。同时我补了 memory_grounded grader 度量"计划文本是否真的用了记忆"——实测只有 33%，说明记忆注入≠计划利用，这是比通过率更深一层的发现，已列为 prompt 迭代目标。我不会拿 +13.3pp 冒充"规划质量提升"——质量维度的证据目前是缺的，grader 就是为了让这个缺口可见。

**边界**：全部预执行的代价是退化成规则引擎，遇到非标输入就僵死。我不接受"稳定性"和"泛化性"二选一，所以分层。

## Q4：「三层记忆？单用户项目搞这个是不是过度设计？」

**结论**：三层各有当下的不可替代作用（L1/L2），只有 L3 是超前预留——而且它是"明确的不做决策"，带量化启用阈值，这正是生产思维而不是堆功能。

**展开**：L1 Run 记忆是会话状态闭环和断点恢复，单用户也必需；L2 Personal 记忆已经在线上起作用——replan 连续性校验依赖它，语义召回带 14 天半衰期和可信度过滤；L3 Shared 当前单租户启用收益为零，还会引入跨用户记忆污染（记忆串台是最难排查的生产事故），所以我刻意不启用。

**数据与阈值**：L2 在用户量 ≥1000 时价值是千人千面（当前评测 case 已验证其必要性）；L3 在用户量 ≥5000 时启用，预期把高频规划模式沉淀为全局模板，省 15–25% 推理 token。

**边界**：如果这个项目永远只有一个用户，L3 就永远不该建——阈值写在迭代计划里，由用户数指标触发，不由技术热情触发。

## Q5：「你的确定性修复只覆盖 4 种规则，来了新规则怎么办？修复成功率 0 的部分怎么兜底？」

**结论**：新规则走三层兜底：LLM 智能归类修复 → 失败降级拦截保底 → 未知违规码自动沉淀成 backlog 离线迭代成新规则——已知规则确定性修、未知规则智能适配、长期场景持续进化。

**展开**：为什么确定性修复只做 4 类：live 评测里这 4 类（REPLAN_CONTINUITY、WEEKLY_FOCUS、FIRST_WEEK_ALIGNMENT、TASK_UNIQUENESS）覆盖了全部观测到的业务违规，且 GLM 自修复成功率是 0/6，所以代码接管是数据决策。未知规则出现时：第一层，交给 LLM 修复（1 次预算），模型对新违规类型有泛化尝试能力；第二层，修复失败走降级模板——schema 合法的保底计划加友好提示，未知规则永远不可能产出非法输出上线；第三层，这次我新增了 unknown_rule 观测闭环：未知违规码打结构化日志、进 Prometheus 计数器、写进 run 事件，归因报告汇总成 backlog，同一规则码反复出现就人工提升为确定性修复。

**数据**：所以规则库是随 badcase 生长的——4 条规则本身就是这么来的，机制已经闭环。

**边界**：承认 LLM 对未知规则的修复成功率目前不高（这正是要降级层的原因），但系统对"修不好"的响应是确定性的：拦截、保底、留快照。且 LLM 修复调用有**量化下线判据**：滚动 100 次调用 rescue rate < 5% 即关闭（归因报告自动输出该比率；当前实测 0/6 已触发，配置旋钮 `BUSINESS_REPAIR_LLM_ENABLED`）；保留角色是未知规则归类探针，backlog 出现新高频码时脉冲开启。修复节点还有独立 30s 超时上限，不再继承整个 Run 的 deadline（repair-03 61s 破线的根因修复）。

## Q6：「你 72% 到 92% 的提升全靠代码兜底绕过模型，模型的 Agent 能力其实没提升吧？」

**结论**：我把优化拆成两个维度分开度量——工程稳定性优化（保可用）和模型能力优化（保好用），92% 这个数字只是工程维度的，模型维度的"一次通过率"我单独有指标，两个都不偷换。

**展开**：工程稳定性优化解决的是"上线可用"：确定性修复消灭致命违规、降级模板保证永远有合法输出、禁用 GLM 隐藏思考把 P95 从 62.5 秒压到 45.5 秒——这些不提升模型智力，提升的是系统可靠性。模型能力优化解决的是"越来越好用"：基于评测沉淀反向优化 prompt 版本、上下文精简（三级压缩）、工具调用逻辑改进——这些提升的是模型一次通过率。两者缺一不可：只有前者是伪 Agent，只有后者上不了线。

**数据（含一次自我纠错）**：① 归因五标签——模型一次通过 83.3%、确定性修复救援 16.7%；② 第一轮基线对照曾显示"裸模型 93.3% > Agent 83.3%"——我后来复核发现那个"裸"臂并不裸（direct 变体仍享预执行记忆与上下文注入），**补跑真裸臂（记忆关+工具关）后：72.4%，live-mem 接地 0/3**——Agent 骨架贡献约 +21pp，之前的"输"是修复环降级质量问题（已修复，k=3 权威口径 88.9%）；③ 记忆消融：k=1 曾见 +13.3pp，k=3 双臂复跑后缩到 +4.3pp（p=0.429，不显著）——我按预注册制度主动撤回了那个数字，记忆层的可证价值定档为接地能力（live-mem 0/3 vs 3/3）+ 零边际成本；④ 恢复能力实测：中断后二次执行 0 次新增物理 LLM 调用（checkpoint 恢复，朴素重跑成本翻倍）；⑤ 盲评（独立 judge，n=8/臂）：记忆层对质量分无显著效应——我主动报告"质量维度证据不足"，因为接地维度的证据（0/3 vs 3/3）已经足够支撑架构价值，不需要拿质量分充数。我连"自己的对照实验曾设计有误"都敢讲——这比任何漂亮数字都可信。

**边界**：承认当前一轮的主要增量来自工程侧——因为 live 数据证明 GLM 在业务规则自修复上就是 0/6，先让系统活下来，模型侧优化是持续迭代项。

## Q7：「为什么不做多 Agent？AutoGen/CrewAI 那么火，是不是不会用？」

**结论**：这是场景取舍不是能力边界——我的任务是单链路、低耦合、延迟敏感（P95≤60s），多 Agent 的通信开销、一致性风险、调试复杂度在这个场景全是纯成本；同时我给出了量化的切换信号，到线就演进。

**展开**：多 Agent 的三项代价在我场景的具体化：通信开销——每多一个 Agent 一轮协商多 1–2 次 LLM 调用，延迟成本线性涨；一致性——多 Agent 各出计划片段，合并后过 21 项校验闸的难度指数级上升；调试——单 Agent trace 是线性的，多 Agent 是图套图。而 AutoGen/CrewAI 的价值场景是复杂多角色协同、长链路任务拆解、多模块分工——我的业务（个人职业规划的生成-校验-修复）一条链路闭环就够。

**数据（切换信号）**：三个量化阈值：修复循环普遍需要 ≥2 轮的 run 占比超 20% → 拆独立 reviewer Agent；工具增长导致调用准确率 <80% → 按域拆 Tool-Router；产品出现多角色需求 → 角色编排。

**边界**：我的图架构预留了扩展位——从单 Agent 到主+子 Agent 是加节点加边，不是重写，这是选 LangGraph 时就埋好的。

## Q8：「你的上下文压缩不就是固定窗口截断吗？跟没做有什么区别？」

**结论**：我的压缩是三级流水线：语义相关性召回、动态 token 预算、摘要式折叠——截断只是其中兜底手段，而且被折叠的信息不丢失，聚合成结构化摘要。

**展开**：第一级，相关性召回：老任务和当前请求做 bigram 重叠打分，高相关的老任务（三周前但和这次请求强相关）会被从摘要区提升回保留区——解决纯近因截断最大的质量风险 recency bias；第二级，动态预算：序列化上下文超过单次调用输入预算时，保留窗阶梯收缩到地板（2 任务/1 复盘），压缩强度随历史长度自适应，不是死窗口；第三级，摘要折叠：移出保留区的任务聚合为"更早完成项/主要阻碍/重复阻碍/调整模式"四类结构化摘要，信息有损但可控、可解释。

**数据**：压缩全程确定性、0 LLM 调用（在必经路径上用 LLM 摘要会加 15–25% 成本和 3–8 秒延迟），每次压缩记录提升条数、收缩步数、前后字符量，效果可观测。

**边界**：LLM 摘要式压缩我留给未来的低频路径（Shared 记忆离线蒸馏），高频路径上确定性聚合的性价比更高。

## Q9：「92% 里模型贡献多少、你的代码贡献多少？说不清就是数据造假。」

**结论**：说得清，而且不是事后估计——是运行时逐 trial 记录的产出路径标签，模型占比和工程占比同源同判。

**展开**：图在 persist 节点给每个 run 写 provenance 事件，五个互斥标签：model_pass 模型一次通过、format_repair 格式自修复、deterministic_repair 代码修复、llm_repair 模型业务自修复、fallback 降级模板。归因脚本把实验的每个 trial 的硬门禁结果和这个标签 join 起来，输出通过 case 的路径拆分、模型能力占比、工程兜底占比，以及失败 case 的路径分布和未知规则 backlog。

**数据**：现场可跑 `python scripts/attribution_report.py`，数据在库里，任何一次 live 实验都能复算。最新实测（30 case，k=1）：通过路径里模型一次通过占 83.3%、确定性修复救援占 16.7%——通过率的大头本来就是模型，工程兜底救的是尾部，两个维度都在涨。

**边界**：注意 format_repair 我计为工程触发、模型执行——它是边界项，我会主动说明归类口径，这种口径透明本身就是评测可信度的一部分。

## Q10：「你这项目上线要多少资源？什么时候撑不住？下一步什么时候做什么？」

**结论**：当前架构在现有量级全部 SLO 达标，每个未建能力都有量化的触发阈值和届时方案——阶段性迭代、按需优化，这是成本和风险的最优解。

**展开**：现在能满足的：单节点 Postgres + 单实例 FastAPI，硬门禁 92.2%、P95 45.5 秒、单 run 成本 1 分钱以内、798 项测试全绿。撑不住的量化阈值：用户破 1 万、QPS 破 50、日均 run 破 10 万时，固定窗口压缩、单节点状态、单机限流、进程内 metrics 会先后成为瓶颈。届时方案全部预研过：限流换 Redis 令牌桶（中间件已抽象，不动调用点）、metrics 换 prometheus-client（模块契约已声明零调用点修改）、分布式状态——我的 lease 本来就是数据库级的，换分布式锁语义不变、Shared 记忆在用户 5000 时启用。

**数据**：每个阈值绑定一个可观测先行指标（用户数、QPS、token 中位数、修复循环轮次占比），指标到线启动迭代，不靠感觉。

**边界**：承认这是单租户演示到小规模生产的架构——如果明天就要接十萬级用户，我给出的第一件事不是堆机器，而是先跑压测把这三个阈值的实测值校准。

## 附：万能兜底句式（被追问到细节时）

1. 承认边界 + 给出度量：「这个我没有做 X，因为我度量过 Y，如果 Y 变了我会做 X」
2. 数据溯源：「这个数字来自哪次实验、多少 case、几次 trial，报告在库里可复算」
3. 取代辩护：「我不是不会用 X，是 X 在这个场景的代价是 A/B/C，收益是零」
